# 技术决策记录（ADR）

这个文件记录**重要的技术选择与放弃**，以及背后的理由。

比代码更重要的，是「为什么这么写」和「为什么不那么写」—— 因为代码会过时，判断不会。

---

## ADR-001：删除「省名搜索兜底」功能

**日期**：2026-10-26
**状态**：已删除

### 背景

用户搜「浙江」「台湾」这类**省名**时，数据源里没有省级条目（AreaCity 从地级市开始），所以最初的结果是空白。

为此加了一个 `provinceFallback`：城市搜不到时，尝试匹配省名，返回该省的地级市列表。

### 实际发生了什么

我在一次项目审查中实测了 21 个用例，**11 个失效**：

| 用户输入 | 用户期望 | 实际返回 |
|---|---|---|
| `zj` | 浙江 | 湛江、镇江、昭觉 |
| `gd` | 广东 | 甘德、官渡、广德 |
| `hn` | 湖南 | 海南、淮南、黄南 |
| `hb` | 河北 | 海北、鹤壁、淮北 |
| `sx` | 山西 | 绍兴、单县、三峡 |
| `sc` | 四川 | 三重、莎车、山城 |
| `xj` | 新疆 | 西吉、峡江、夏津 |
| `tw` | 台湾 | 泰武、汤旺、田尾 |

### 根因（三层，一层比一层糟）

**第一层：触发条件写错了。**
`provinceFallback` 只在「城市搜索结果为空」时才执行。但 `zj`/`gd`/`hn` 这类简拼**永远能匹配到真实城市**（湛江、甘德、海南都是真地名），所以兜底逻辑**永远不会执行**。

**第二层：用伪造别名掩盖。**
发现 `hn` 冲突后，加的是 `hn2`（湖南）、`hn3`（河南）、`hb2`（河北）、`sx2`（陕西）、`gz2`（贵州）—— 这些**不存在于任何输入法中**。等于承认 bug 但不修，加后门让测试通过。

**第三层：测试把 bug 写成了正确行为。**

```js
// scripts/test-province-fallback.mjs 里的原句
✅ 「tw」命中真实城市（泰武）而非兜底
```

一个 15/15 全绿的测试套件，**明确断言了错误的行为**。

### 决策：删除，不修

**修复的成本**：
- 重构搜索优先级（省份结果要和城市结果混排）
- 处理「省份结果 vs 城市结果」的排序权重
- 重写测试（现有测试的断言方向是错的）

**保留的价值**：
- 城市搜索已经覆盖 90% 真实场景
- 想找浙江省的城市，搜「杭州」比搜「浙江」快
- 一个半成品功能，在面试时是负资产

**结论**：删除。同时删除 `test-province-fallback.mjs`（测的是错误行为）。
顺带清理 4 个从未被调用的导出：`CITY_COUNT_LEVEL1`、`getCityById`、`_score`、`includeDistricts`。

### 教训

> **测试全绿 ≠ 功能正确。**
> 如果测试的期望值是照着实现抄的，那它测的是「代码和它自己一致」，不是「代码符合需求」。

**以后写测试先问一句：它测的是源码逻辑，还是我抄的一份副本？**

## ADR-002：城市数据离线生成，运行时零依赖

**状态**：生效中

### 背景

调研发现：**没有任何 npm 包同时提供「城市名 + 拼音 + 经纬度」**。

| 类型 | 代表包 | 缺什么 |
|---|---|---|
| 行政区划包 | `cn-division`、`china-area-data` | 无经纬度、无拼音 |
| 拼音库 | `pinyin-pro` | 只有转换能力，无城市数据 |

而且 `china-division` 解压后 **190MB**，装进 Next.js 会拖垮构建。

### 决策

用脚本从 [AreaCity](https://github.com/xiangyuecn/AreaCity-JsSpider-StatsGov) CSV 离线生成 `src/lib/cities.json`（3563 条），坐标用 Open-Meteo Geocoding 批量补齐，**结果提交进仓库**。

### 后果

- ✅ 运行时零依赖，首屏不受影响
- ✅ 数据可审计、可手改
- ⚠️ 数据更新需要重跑脚本（`scripts/` 里有完整流程）
- ⚠️ 29% 的区县坐标是「继承所属地级市」的近似值（`coordSource: "fallback-city"`）

## ADR-003：生活提醒用国标，不用「穿衣公式」

**状态**：生效中

### 背景

网上流传「26℃ 穿衣公式」（厚羽绒服 = 9℃，用 26 减去气温做加法）—— 这个公式**被中国气象局公开否定**：

> 「即使同样的气温，南方和北方给人的感觉完全不一样；就算同一个地方，同样的气温，是否有太阳、是否有风给人的感觉也不一样。」

### 决策

- **穿衣**：依据 **QX/T 385—2017《穿衣气象指数》**（中国气象局行业标准），7 级分档，文案逐字抄录
- **紫外线**：依据 **GB/T 36744—2018《紫外线指数预报方法》**，5 级分档
- 用 `apparentTemperature`（体感温度）而非裸气温 —— 体感已综合湿度、风速、辐射

### 后果

- ✅ 比 90% 同类产品更权威
- ⚠️ 国标的 `Tm` 参数需要当地历史气候数据，本项目用体感温度做工程近似（已在 `life-tips.data.ts` 注明）
- 详见 `docs/生活提醒-竞品调研与设计方案.md`

## ADR-004：不给用户看等级数字

**状态**：生效中

### 背景

调研发现中国天气网自己的页面存在**等级方向混乱**：

```
洗车指数：三级 = 不适宜    ← 数字越大越差
行驶指数：一级 = 好        ← 数字越小越好
晨练指数：四级 = 适宜      ← 又反过来了
```

同一页面，同一个「等级数字」，方向不统一。中国气象局在制定穿衣标准时正是点名批评了这个问题。

### 决策

**只输出文案，不输出等级数字。**

```
✅「☂️ 带伞出门」
❌「雨伞指数：2 级」
```

## ADR-005：测试要测真源码

**状态**：生效中

### 背景

最早的生活提醒测试脚本（`test-life-tips.mjs`）是**把阈值抄一份**再测：

```js
// ❌ 测的是副本
const DRESSING_LEVELS = [
  { max: -10, short: "厚羽绒服 + 手套" },
  ...
];
```

**源码改了，测试照样绿。** 这叫「假测试」，比没测试更危险 —— 它给虚假的安全感。

### 决策

用 `tsx` 直接 import TS 源码：

```js
// ✅ 测的是真东西
import { buildLifeTips, pickBannerTip } from "../src/lib/life-tips.ts";
```

### 后果

- `scripts/verify-life-tips-boundary.mjs` 覆盖 38 条用例（真源码）
- 发现并修复了穿衣/运动边界值的 off-by-one（体感正好 5℃ 会跳档）

## ADR-006：苹果风浅色，靠色差造层次而非阴影

**状态**：生效中

### 决策

- 页面底 `#f5f5f7`，白卡浮于其上，**无边框无阴影** —— 靠 2% 亮度差造层次
- 全页只有一个彩色 `#0071e3`，只用于交互
- 大数字温度用 `font-extralight`（200 字重）

### 关键坑

**深色版的亮蓝不能直接搬到浅色**：

| 颜色 | 深色底 | 白底 |
|---|---|---|
| `#60a5fa`（原强调色） | 7.74:1 ✅ | **2.54:1 ❌ 不达标** |

浅色必须换深一档（`#0071e3`），且 **11px 小字要用 `#0066cc`**（`#0071e3` 只有 4.70:1）。

详见 `docs/apple-light-design-research.md`。
